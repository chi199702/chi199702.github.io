SpinLock

一、基本概念

在多线程环境下，自旋锁被用于保证线程之间的同步。不同于互斥锁，自旋锁在获取锁失败时不会放弃使用 CPU，而是通过轮询的方式来不断的忙等待锁的释放，直到获取到锁才结束循环。

自旋锁的特点：自旋等待，若获取不到锁，则进入自旋等待，且是一直消耗 CPU 资源来忙等待的方式，直到获取到锁为止。

二、适用场景

自旋锁的性能问题(1)

  • 除了获取到锁后进入临界区的线程在工作，其他处理器上的线程都在空转
  • 争抢锁的处理器核心越多，利用率越低
    • 10 个 CPU 在使用 spinlock 来 sum++，任意时刻只有一个 CPU 在 sum++

自旋锁的性能问题(2)

  • 当线程数量比处理器核心的数量多时，持有 spinlock 的线程可能被操作系统切换出去
  • 存在一种情况，当持有锁的线程被切换出去后，得到时间片的线程也在忙等待 spinlock，即实现了 100% 的资源浪费:sweat_smile:

使用场景

  1. 持有自旋锁时禁止执行流切换

    内核有特权关闭中断核抢占，所以在操作系统内核中可以使用自旋锁来设计一些短临界区的并发数据结构

  2. 在用户空间中，自旋锁应该被使用在线程临界区几乎不拥堵的场景下，即对自旋锁的竞争不激烈

    当我们明确知道获取到 spinlock 的线程只会短暂的占据临界区就退出，且抢锁的线程数量不多时，我们是可以使用自旋锁的。占据临界区的时间越短，受到执行流切换的影响就越小。

三、API

1. 初始化锁/销毁锁

两个函数的返回值：成功，返回 0；否则，返回错误码

  • pthread_spin_init : 初始化自旋锁，当其第二个参数pshared的值是PTHREAD_PROCESS_SHARED时，自旋锁可以被不同进程中的线程使用，前提是系统支持，并且进程拥有访问自旋锁所在内存的权限；当值等于PTHREAD_PROCESS_PRIVATE时，自旋锁只能被初始它的进程内部的线程使用。

2. 加锁/解锁

三个函数的返回值：成功，返回 0；否则，返回错误码

  • pthread_spin_trylock : 不会自旋，加锁失败后直接返回错误码

四、汇编代码

系统环境

使用 objdump -D /usr/lib64/libpthread-2.17.so命令反汇编后提取出和 spinlock 相关的汇编代码

1. pthread_spin_init

  1. 自旋锁可以看成是计数器，刚开始时被初始化为 1

  2. %rax 寄存器用于存储函数的返回值，而 %eax 是 %rax 的低 32 位部分

2. pthread_spin_lock

  1. lock 指令前缀的作用：在执行被 lock 前缀修饰的指令时，处理器会发出 lock 信号来锁住总线从而让被修饰指令变成 1 条原子指令。在多处理器环境下，当 lock 信号被发出后，会确保发出该信号的处理器对共享数据的访问具有排他性。所以lock decl (%rdi)是一条原子指令，其对 lock 的read-modify-write这个过程是不可中断且 lock cache line 的，就不会出现多个线程同时观察到锁是空闲的情况。
  2. 在 unlock 状态时，decl指令会让锁的值由 1 -> 0，那么 zero flag 被置为 1，jne指令就不会发生跳转，此时获取到了自旋锁，直接返回。而在 lock 状态时，decl 指令会让锁的值变成负数，zero flag 被置为 0，jne 指令生效跳转到pause指令。pause指令类似于Execute_Next_Instruction(DELAY)的作用，在 delay 一会后通过再次查看锁的值来决定是继续 delay 还是尝试获取自旋锁

3. pthread_spin_unlock

奇怪的是在汇编代码中找不到pthread_spin_unlock的代码，通过readelf -Ws libpthread-2.17.so查看符号表

Value 表示函数的起始地址，Size 表示函数体的字节大小，Type 等于 FUNC 表示该符号是个函数。提取出和 spinlock 相关的符号后发现pthread_spin_init的起始地址和上述汇编代码中的地址是相同的，而且pthread_spin_init和pthread_spin_unlock具有相同的起始地址和大小。

据此可以断定的是pthread_spin_init和pthread_spin_unlock的功能是一样的，即都是把锁的值置为 1，表示锁是可获取的状态。

1. pthread_spin_init

使用 relaxed 内存序原子的把 lock 的值置为 0，这一点和 libpthread-2.17.so 不同。

2. pthread_spin_lock

  1. 在源文件的注释中有提到，假设大部分情况下首次尝试抢锁就会成功，并且认为xchg的性能比cmpxchg的高，所以优先选择使用atomic_exchange。atomic_exchange_acquire让 lock 和 1 进行原子性的交换，如果拿到的 lock 值是 0，说明获取到了锁。atomic_exchange_acquire函数内部使用__atomic_exchange_n来实现，其是 gcc 提供的原子操作，并且使用了 acquire 内存序，保证了在读取锁时已经刷新其他线程对锁的原子操作，读的最新值。

    结合自旋锁适用于竞争不激烈且对锁占用时间短的场景来看，首次抢锁就成功的概率是不小的。

  2. 如果当前架构没有xchg指令，选择使用cmpxchg指令。atomic_compare_exchange_weak_acquire通过比较val(0) 和 lock 的值，如果相等(锁是空闲的)就把 lock 置为 1(抢锁成功)。同样使用 acquire 来保证同步。

  3. 到此说明锁已经被占用了，需要自旋等待。atomic_spin_nop的作用同上述分析汇编代码中的PAUSE 指令

  4. 使用 relaxed 内存序来原子的读锁的值

  5. 当锁的值不等于 0 就说明锁被占用，否则跳出循环

  6. 使用cmpxchg来再次获取锁

值得思考的是在 6 中为什么不像 1 先尝试使用xchg指令而直接使用了cmpxchg？Inter 开发手册中描述cmpxchg时指出 destination operand receives a write cycle without regard to the result of the comparison.(CMPXCHG—Compare and Exchange Vol. 2A 3-213)，即 cmp 后是否成功都会进行 write cycle。也有研究指出xchg和cmpxchg的性能几乎一样……所以这个问题暂且保留。

3. pthread_spin_unlock

使用atomic_store_release原子的把锁状态置为 0，其和pthread_spin_init的功能一样，这也验证了在上述汇编代码分析中我们断定的解锁和初始化的代码功能是一样的

pthread_spin_lock中的 acquire 内存序和pthread_spin_unlock中的 release 内存序配合，lock 和 unlock 的多个线程间达到了同步。

六、拓展

1. memory order

仅仅依赖于原子操作并不能解决全部的同步问题，原子内存序定义了原子操作之间的顺序以及这些操作与程序其他部分的交互方式。它影响了编译器优化、指令重排序、处理器缓存的行为，选择合适的内存序对于实现高效且正确的多线程程序至关重要。

  1. memory_order_relaxed : 只保证操作的原子性，对其他的读写操作没有同步或者顺序要求，不对编译器和处理器的优化做任何限制，常用于不需要严格同步的场景，比如计数器。

  2. memory_order_acquire : 用于原子读取，load 之前的(不同线程的)指令不能重排序到 load 之后，并刷新缓存，保证使用该内存序的线程可以读取到最新的值。

  3. memory_order_release: 用于原子写入，store 之后的指令不能重排到 store 之前，并刷新缓存，保证当前线程写入的值对其他线程可见。memory_order_release 和 memory_order_acquire 配合使用可以实现线程同步。

  4. memory_order_acq_rel: memory_order_acquire 和 memory_order_release 的结合，read-modify-write 时使用。

  5. memory_order_seq_cst: 默认内存序，也是最严格的内存序，所有原子操作都按照程序中的顺序来执行，所有线程的操作都是相互可见的，所以限制了编译器和 CPU 对指令的优化，造成性能损失最大。

2. 缓存一致性

  1. snoop

    监听/嗅探协议，在多核处理器中，每个核都是一个 snooper，所有 snoopers 通过总线来连接且每个 snooper 都会监听总线，当某个核修改了数据，就会产生一个 transaction ，该核会通过总线广播的方式来传播该 transaction ，其他所有核都会检测自己的 cache 中是否存在该数据副本，存在的话 flush 或 invalidate cache block，以此来达到缓存一致的效果。MESI(modify exclusive shared invalidated)协议就是 snoop 协议。

  2. directory

    目录协议，相比于 snoop 在每个核中增加 snoop filter，directory 协议设置一个中央目录、来统一记录所有核的 cache 状态。每个核进行读写时导致的 cache 状态变更都会同步到中央目录中。实现 directory 协议有多种方式，如 Full bit vector format、Coarse bit vector format、Sparse directory format 等等。

snoop 协议由于使用的是广播机制，对总线会产生较大的带宽压力，所以其适用于规模不大处理器系统。directory 协议相比于广播的方式，大大减少了总线中 transaction 的数量，但对硬件有更高的要求。

九、修改点

  • 修改绑核代码，应该在每个线程的执行体内进行绑核
  • 测试开始时间不应该放在线程创建之前，应该放在线程创建完之后，开始进入临界区之前，并且刚开始时 CPU 频率还没起来，所以先让每个线程空转几 ms 再说，或者设置 1 个标志位，等待每个线程都初始化完以后再开始计时
  • C 代码的 libc-2.17 的代码看错了，应该看 ports/sysdeps/ia64 下面的代码
  • memory_order 理解得还不够深，特别是 acquire 的内存序
  • 了解 PAUSE 指令
